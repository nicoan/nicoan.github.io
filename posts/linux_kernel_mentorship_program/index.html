My experience in the Linux Kernel Mentorship Program

September 18, 2026 · 6 min · Nicolás Antinori

Contributing to the Linux kernel is something that I wanted to do since I got interested in programming. I never did it (until now!) because it felt too big, it was not an easy decision to start contributing to one of the biggest and most important projects of the open source space. After having contributed to some other open source projects, I decided that it was time that I give Linux a try. After all, it is a piece of software that I use on daily basis, it aligns with my interests in systems programming and it is a project where I can learn a lot because it is built by experts.

So, the decision is made, but where do I begin? Searching on the internet how I could get started1 I found the Linux Kernel Mentorship Program and decided to apply.

Application Process#

The application process requires you to complete “A Beginner’s Guide to Linux Kernel Development (LFD103)”, a free course by the Linux foundation that teaches you the basics of the kernel development process and how to interact with the community. Along with that, other tasks are given to you, some to evaluate your software development skills and some to evaluate your problem solving skills. I recommend you to take them seriously.

The program usually receives a lot of applications, and there are a lot of talented people out there, so I did not have high hopes of getting accepted. On 5th of June I received an e-mail confirming that I was accepted! I was thrilled!

The First Weeks#

Even though I am used to get familiar with big new codebases, the Linux kernel is a different beast. The kernel is divided into several subsystems that manage a different aspects. At the beginning of the program, we are told to focus in two subsystems at most, and believe me, this is a very valuable piece of advice. The kernel is huge, and each subsystem has its own peculiarities and conventions. Focusing on various subsystems at the same time means learning a lot of different and new information at the same time.

At the beginning it is normal to feel a little bit lost. A common question arises among mentees “What subsystems do I choose?”. My recommendation here is, stay away from core subsystems (such as memory management) since those require a lot of expertise, and go with what you are most interested in. In my case I chose the DRM subsystem in charge of managing everything related to rendering graphics, a topic I find very interesting, and IIO Subsystem because I wanted to learn how to write device drivers2 by starting with the simplest ones. I also checked the Rust for Linux project, because, as you can see in a lot of other posts on this blog I am really interested in the Rust programming language!

The General Experience#

The program is designed to be self-driven on purpose, because it is what open source contributors experience. This means that you are in charge of finding where to contribute, learn what is needed to generate a patch and send it to the mailing list.

Since it is a self-driven program, a lot doubts about different topics will surely arise. To solve them, a one-hour weekly meeting is held where mentors will answer questions and explain different things. Along with those, some other things that really helped me were to ask questions directly to other more experienced mentees (some people in the program already have some kernel development experience), read the mailing list periodically and read the documentation of the subsystems I chose.

The program also prohibits the use of AI, and this is a good thing. Using AI interrupts the learning process. To learn, you need to struggle.

The Myth#

There is a myth that the Linux kernel community is a harsh one. That when you send a patch you will get no friendly suggestions or you will be insulted. That is not true, at all. Maintainers are people too, and they are usually busy, their feedback is concrete and goes straight to the point for the sake of efficiency, but no one will mistreat you. Also, getting feedback from experienced kernel developers is of immense value.

Demonstrate that you invested time to understand what you are doing, put effort on the patches you send and be willing to continue working on them when you receive feedback. Be respectful of the other person’s time.

From Small To Not-So-Small Patches#

My first patch was a very small one: an optimization in the Rust’s OPP module that removes intermediate symbols generated by clang for methods that are just a wrapper of C functions. I still remember the sensation when I received the e-mail confirming that it was applied! More small patches followed this one, but as I became more familiar with the code (and the subsystems I chose) I increased the complexity of the things I worked on. It is recommended to start sending patches early on the program. Don’t be afraid to send simple ones, you have to start somewhere.

Currently, I am working in a DRM driver for the CH1115 controller, a simple driver, but that requires dealing with different subsystems (i2c, DRM) and different kernel APIs.

Conclusion#

I had a really good experience going through this program. The chance of being part of the kernel community and being able to contribute to such an important project is priceless to me.

I am very grateful to my mentors Shuah Khan, Brigham Campbell and Jori Koolstra for all the patience and guidance. The program definitely made things easier, seeing people struggling with the same things as I, and having mentors to help with those struggles and the general process of becoming a kernel developer is highly encouraging for newcomers. Thanks to them and the program I achieved my long time objective of contributing to the Linux kernel.

My plan is, of course, to continue contributing.
